# Harness Creator

Adapts material from [walkinglabs/learn-harness-engineering](https://github.com/walkinglabs/learn-harness-engineering) (MIT — see `NOTICE.md`).

## Purpose

A harness is everything around the model — instructions, state tracking, verification, lifecycle handling — that determines how much of the model's actual capability gets realized in practice. "The model is smart, the harness makes it reliable." This skill scaffolds a harness for the repo it's run in, tailored to a specific scenario (e.g. "set up testing infrastructure," "prepare this repo for long multi-session work").

## The five-subsystem model

| Subsystem | Responsibility |
|---|---|
| Instructions | Project overview, tech stack, first-run commands, hard constraints |
| Tools | Least-privilege agent access |
| Environment | Reproducible runtime (lockfiles, version pins) |
| State | Long-task progress tracking |
| Feedback / Verification | Explicit, runnable verification commands — the highest-ROI subsystem |

## Applied components (what this skill actually generates)

| Component | Artifact | Path |
|---|---|---|
| Instructions | `CLAUDE.md` or `AGENTS.md` | repo root (target-dependent, see below) |
| State | `feature_list.json` | `.agent/feature_list.json` |
| Verification | `init.sh` | `.agent/init.sh` |
| Scope | dependencies + done criteria, encoded inside `feature_list.json` | `.agent/feature_list.json` |
| Lifecycle | `progress.md`, `session-handoff.md` | `.agent/` |

## Target contract

`target` controls the **format of the generated instructions file** — it has nothing to do with which AI clients can run the `/harness-creator` command itself (that's controlled separately, by this package's own `apm.yml` `targets:` field). Don't conflate the two.

| `target` | Instructions file | Location | Extras |
|---|---|---|---|
| `claude` | `CLAUDE.md` | repo root | optional `.claude/agents/*.md` — only if the scenario genuinely needs a sub-agent (see "Sub-agents" below); not generated by default |
| `copilot` (**default**) | `AGENTS.md` | repo root | `.github/copilot-instructions.md` pointer stub — only if explicitly asked for, never by default |
| `cursor` | `AGENTS.md` | repo root | none |

If `target` isn't given, default to `copilot` — regardless of which client is actually running this command. That default was chosen deliberately, not a bug.

## Output location

Everything except the one root instructions file (and, if warranted, Claude sub-agent files) is written under `.agent/` in the **consumer repo** — the repo this command is run in. Nothing is ever written back into `adra-agent-plugin` itself or into `apm_modules/`.

## Workflow

1. **Audit.** Using Read/Grep/Glob, check the consumer repo for: an existing `AGENTS.md`/`CLAUDE.md`/`.github/copilot-instructions.md`, an existing `.agent/` folder, test/build tooling, README, CI config, and manifest files (`package.json`, `*.csproj`/`*.sln`, `requirements.txt`/`pyproject.toml`, `go.mod`, `Cargo.toml`, `pom.xml`/`build.gradle`).
2. **Ask only for what's missing.** `target`, if not supplied (else default `copilot`). Clarify the scenario if it's too vague to act on. If the audit found existing artifacts, **ask before overwriting** — never silently clobber.
3. **Decide scope — minimal first.** Default to the five core artifacts plus one instructions file. Only add sub-agents, extra reference docs, or extra feature entries if the stated scenario specifically calls for them. This mirrors the harness-engineering principle "favor minimal scope initially, expand only when required."
4. **Run the scaffolder.**
   ```
   node scripts/create-harness.mjs --client <claude|copilot|cursor> --out-dir <repo root> --state-dir .agent --scenario "<what the user described>" [--force]
   ```
   This writes the mechanical skeleton only — stack detection, verification commands, placeholder prose. If `node` isn't available in the execution environment, fall back to hand-authoring the six files directly from `templates/` (read each template, substitute the same `${TOKEN}` placeholders by hand: `PROJECT_NAME`, `STACK`, `PACKAGE_MANAGER`, `STATE_DIR`, `AGENT_FILE`, `SCENARIO`, `GENERATED_AT`, `VERIFICATION_COMMANDS`) rather than failing outright.
5. **Fill in real content.** Replace every `TODO` in the generated instructions file with content actually grounded in the audit from step 1 — real project context, real conventions, real constraints. Write real `feature_list.json` entries for the actual scenario, not the generic placeholders the script left behind. Decide which `references/*.md` (see index below) are relevant enough to copy into `.agent/references/` for this specific scenario.
6. **Verify.** Actually run `.agent/init.sh` (or the equivalent commands it documents) and capture real output. Only populate a feature's `evidence` field, or mark it `pass`, once verification has actually run — never accept self-report as evidence.
7. **Report back.** List every file created or updated with its exact path, flag any placeholders still left unresolved, and remind the user that harnesses rot like code — this should be revisited periodically, not treated as one-and-done.

## Sub-agents (target=claude only)

Only generate a `.claude/agents/*.md` file when the scenario explicitly implies a distinct, narrowly-scoped role that should run separately from the main work — e.g. a dedicated reviewer/verifier agent, or a role that needs a different tool whitelist than the main session. Keep it small: `description` (required), 2-sentence role/scope opening the body, explicit boundaries (what it will and won't do), expected deliverables. Don't default to creating one — most scenarios don't need it, and an unnecessary sub-agent adds coordination overhead without benefit.

## Reference index

Load these only when their trigger condition is actually met — don't load speculatively.

| File | Load when… |
|---|---|
| `references/gotchas.md` | Before finalizing any harness — a fast pre-flight check against 15 known failure modes. |

| `references/lifecycle-bootstrap-pattern.md` | The scenario involves multi-session work or anything that needs to survive a restart — directly relevant to `session-handoff.md`. |

## Boundaries / non-goals

Not for model selection, prompt tuning, UI design, or general architecture decisions unrelated to agent reliability. Never modifies `adra-agent-plugin` itself — all output belongs to the consumer repo.

## Safety rules

- Never delete or overwrite existing user content without explicit confirmation.
- Never auto-commit or run `git add` on generated files — leave that to the user.
- Scripts invoked by this skill are side-effect-free outside `--out-dir` and `--state-dir`.
