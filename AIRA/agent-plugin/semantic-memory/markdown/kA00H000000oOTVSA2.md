Setup Federating with Adra
==========================

Introduction
------------

Adra offers services like Balancer and Task Manager to streamline the month-end close process. Additionally, Adra provides a Setup portal for System Administrators to configure customer-specific settings and users.

All services use a common login page for authentication.   
The following login options are available:

1.  Default password and account locking policies
2.  Custom password and account-locking policies
3.  Federated Identity Provider for Single Sign-On.

###   
Federated Identity and Single Sign-On

Federated identity management allows organizations to use the same identification data to access secure content. This is closely related to Single Sign-On (SSO), which lets users access multiple applications with one username and password. SSO authenticates users for all their authorized applications, eliminating further prompts during a session. This document provides a technical overview of Adra's SSO solution. 

###   
SAML

Security Assertion Markup Language (SAML) is an XML standard for exchanging user authentication data between secure web domains. It allows an online service provider to authenticate users via a separate identity provider.

Adra offers a SAML-based Single Sign-On (SSO) service, giving customers full control over authentication. In this model, Adra acts as the service provider, offering services like Balancer and Task Manager, while customers act as identity providers, managing user authentication. There are many open-source and commercial identity provider solutions available to help implement SSO with Adra.

Adra's SSO service follows SAML v2.0 specifications, supported by vendors like Microsoft Active Directory Federated Services, IBM Tivoli, and cloud services such as Okta and OneLogin.

  
 

Execution/Flows
---------------

Adra supports both service provider-initiated sessions, where the authentication session is started by Adra, and identity provider-initiated sessions, where the session is started at the customer site.

###   
Service Provider Initiated Session

The user navigates to any Adra service and is redirected to the common login page to enter their username. If the login page detects that the user is set up to use a Federated Identity Provider, the user is redirected there for authentication. Once authenticated, the user is returned to Adra and redirected to the service where they initiated the session.   
  
![image](https://static.adra.com/adra-assistant/images/c5071d7b3291caebea990062f30cc695.jpg)

1.  The user attempts to access an Adra application, such as Balancer, Task Manager, Matcher, Journal Entry, or another service.
2.  The user is presented with the Adra Login page.
3.  The user enters their username.
4.  Adra recognizes the user as configured for a Federated Identity Provider and generates a SAML authentication request (AuthnRequest).
    *   The request is encoded and embedded into the configured login URL, including the RelayState parameter, which contains the encoded URL of the Adra application the user is trying to reach.
        
5.  Adra sends a redirect to the user's browser with the encoded authentication request.
6.  The customer's identity provider decodes the request.
7.  The identity provider authenticates the user if not already done.
8.  The identity provider generates a SAML authentication response containing the authenticated user's username (email address). This response is digitally signed with the customer's private key, as per the SAML 2.0 specification.
9.  The identity provider encodes the response and the RelayState parameter and returns this information to the user's browser.
10.  Adra verifies the response using the customer's public key. If the response is successfully verified, Adra redirects the user to the destination URL specified in the RelayState parameter
11.  The user is logged into the service.

###   
  
Identity Provider Initiated Session

This flow is similar to the Service Provider Initiated Session but skips the initial steps.

In this scenario, the user is already authenticated at the customer site and uses a link, such as on an application board, to access an Adra service directly without going through the login page. The RelayState attribute determines which service the user is redirected to. For example, a valid value would be `[https://balancer.adra.com](https://balancer.adra.com)`. If the value is invalid or left empty, the user will be redirected to the Setup portal (`[https://setup.adra.com](https://setup.adra.com)`).

Frequently Asked Questions (FAQs)
------------------------------------

**How is the Metadata URL used?**  
  
Adra uses the Federation metadata URL to update the SAML configuration for external identity providers. The configuration is automatically updated every 24 hrs. This includes the default configuration and the certificates used in the authentication process. This also allows us to support certificate rollover scenarios.  
  
**How can I override the default configuration?**  
  
You can override the default configuration by toggling On the override toggle button on the SAML Configuration section header. This will allow you to configure the SAML endpoints, Algorithms, and the other available configuration options.  
  
**What happens to the overridden configuration when the SAML configuration is updated every 24 hrs?**  
  
When the override toggle is set to On, the 24-hour update process will not update the overridden configuration options. But it will update the certificates used for SAML authentication.  
  
**Can I manually force the SAML configuration update?**  
  
Yes. If you have a Federation Metadata URL set, if you click on the Update button, it will update the configuration options (some configurations depend on whether you have the override toggle On or Off). But it will update the SAML certificates.  
  
**Are there any recommendations when configuring an External Identity Provider?**  
  
We recommend not to use SHA1 as signature and digest algorithms. It’s available for supporting existing customers who have not migrated to SHA 256 yet. We recommend using SHA-256. When creating a new configuration, signature, and digest algorithms will be set to SHA 256 by default.  
  
Also, we recommend not using Embedded Certificates by enabling the toggle.  
  
**I am a customer with an existing external identity provider configuration. Should I be worried about these changes?**  
  
No. We support existing customers with external identity providers without changing the current configuration. They will continue to work. But we do recommend using the Federation Metadata URL of your Identity Provider (eg. AD FS) and allowing the configuration to be automatically updated every 24 hrs.  
  
**I want to configure Azure AD as an Identity Provider.**  
  
Please follow the documentation on Using Azure AD with Adra to learn how to configure Azure AD.  
  
**What are the common SAML authentication issues?**  
  
Please follow the documentation on Common Issues with SAML Authentication to troubleshoot SAML authentication issues. If that does not solve your issue, please contact the Adra support team.  
  
**Does Adra integrate with Okta?**  
Okta is an application used for signing onto different applications. Okta provides a large variety of settings and can be set up for the Adra Product Suite. Yes: [https://login.adra.com/saml/federationmetadata](https://login.adra.com/saml/federationmetadata)
